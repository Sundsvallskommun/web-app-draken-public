1

Rekommendation i korthet

Behåll ärendet generellt. Låt JSON Parameters äga formulärdata, AccessMapper äga gruppregler och Support Management verkställa beslutet vid varje läsning och skrivning.

1 · Instansdata

En parameter per del

Varje utredningsdel får egen key, schemaId, data och version.

2 · Konfiguration

Serverägd sektionsdefinition

Definitionen anger titel, ordning, schema och stabil resursnyckel för behörighetskontroll.

3 · Policy

Separat AccessMapper-typ

Använd exempelvis errandSection. Blanda inte sektionsrättigheter med labels.

4 · Verkställighet

Backend kontrollerar alltid

Frontend visar capabilities, men varje GET, PUT och DELETE auktoriseras på nytt av backend.

Föreslaget beslut: inför inte investigationPart1, investigationPart2 och investigationPart3 som nya fasta fält på Errand. Återanvänd den generella JSON Parameter-mekanismen och lägg endast till den minsta generella skarven som behövs: en sektionsdefinition och en nyckelbaserad behörighetskontroll.
2

Så ser ett ärende ut idag

I Draken hämtas JSON Parameters fortfarande som en lista i hela ärendet och visas skrivskyddat under ”Ärendeuppgifter”. Support Management 14.14 har dessutom fått dedikerade GET-, PUT- och DELETE-endpoints per parameter-key, men Drakens BFF använder dem ännu inte.

Förenklad Errand i Drakennuvarande presentationsväg 
{
  "id": "f3f8…",
  "errandNumber": "IAF-2026-1042",
  "status": "UNDER_INVESTIGATION",
  "labels": [
    { "resourcePath": "IAF/DEVIATION/MEDICATION" }
  ],
  "parameters": [
    { "key": "source", "values": ["E-tjänst"] }
  ],
  "jsonParameters": [
    {
      "key": "caseData",
      "schemaId": "2281_iaf-case-data_1.0",
      "value": { "reportedEvent": "…" }
    }
  ]
}

Vad Draken gör med datat

  • Det incheckade kontraktet har key, schemaId och value, men ännu inte 14.14-fältet version.
  • BFF-modellen accepterar jsonParameters[] i samma DTO som övriga ärendefält.
  • Generell PATCH vidarebefordrar inkommande ärendedata utan If-Match.
  • Frontend hämtar JSON Schema och UI Schema via BFF och renderar parametern skrivskyddat med RJSF.
  • Om UI Schema saknas låter Draken formulärkomponenten skapa en standardlayout.
  • Labels används för klassificering och ärendets nuvarande accessberäkning.

3b

Hur JSON Schema och UI Schema lagras

JsonSchema-tjänsten är rätt ägare för formdefinitionerna. Den ska däremot inte bära rättigheter, workflowstatus eller användarens ifyllda utredningsdata.

Versionsregler i JsonSchema

  • ID skapas som municipalityId_name_version och normaliseras till gemener.
  • JSON Schema skapas med POST; en befintlig version ersätts inte.
  • En lägre version får inte skapas efter att en högre version finns.
  • UI Schema är exakt ett per JSON-schemaversion och kan ersättas med PUT.
  • UI Schema har inget eget versionsnummer eller ETag; samtidiga uppdateringar är i praktiken last-write-wins.

Konsekvens för tre utredningsdelar

  • Skapa ett JSON Schema och ett UI Schema per del och version.
  • Lagra exakt schema-ID på motsvarande JSON Parameter.
  • Använd en namngivningskonvention som inkluderar domän/namespace; tjänsten isolerar bara per kommun.
  • Versionssätt JSON Schema när en UI-förändring måste vara reproducerbar för äldre ärenden.
  • Lagra aldrig R/RW, AD-grupper eller workflowlås i UI Schema.
Scopebeslut: JsonSchema-tjänsten ingår i lösningen som katalog, validerare och presentationskälla. Den ingår inte som policy-store. Sektionsrättigheter ska fortsatt ägas av AccessMapper och verkställas av Support Management.

Så förhindras alternativa åtkomstvägar

En ny säker endpoint hjälper inte om samma data fortfarande kan läsas eller skrivas genom hela ärendet, historik, export eller överlämning.

Kontroller vid läsning

  1. Hämta användaridentitet från betrodd kontext.
  2. Kontrollera kommun, namespace och ärendet.
  3. Slå upp sektionen från URL-nyckeln.
  4. Slå upp serverägd accessresurs.
  5. Kräv R eller RW från AccessMapper.
  6. Returnera inte värdet vid nekad access.

Ytterligare kontroller vid skrivning

  1. Kräv RW på både ärende och sektion.
  2. Kontrollera eventuell workflowlåsning.
  3. Kräv att schema hör till sektionens nyckel.
  4. Validera data mot JSON-schemat.
  5. Kräv korrekt If-Match för just parametern.
  6. Auditlogga vem, sektion, tid och revision.
Deny by default: okänd sektionsnyckel, saknad AccessMapper-regel, otillgänglig AccessMapper eller en schemaidentitet som inte hör till sektionen ska aldrig falla tillbaka till generell RW på ärendet.
7

Minsta reviewbara genomförande

Bygg endast den generalitet som de tre riktiga sektionerna kräver. Behåll en tydlig förlängningspunkt för andra verksamheter, utan att skapa ett abstrakt resurssystem i förväg.

1

Definiera layout

Tre keys, titlar, versionssatta JSON/UI-scheman och accessresurser för IAF.

2

Konfigurera AccessMapper

Ny typ errandSection och R/RW per AD-grupp.

3

Central auktorisering

En kanonisk backendfunktion för case + section + operation.

4

Fördjupa befintliga endpoints

Återanvänd GET/PUT/DELETE per key; lägg till schema-validering, audit, databasunikhet och obligatorisk If-Match.

5

Stäng bypassvägar

Filtrera eller ta bort JSON-data från generisk GET, PATCH, export och historik.

6

Bygg Draken-vyn

Manifest, capabilities, tre undertabbar och separat spara per parameter.

Acceptanskriterier

  • En användare utan READ kan inte läsa data via någon endpoint eller export.
  • En användare med R men utan RW kan inte ändra delen, även med manuellt API-anrop.
  • Två användare kan spara olika keys utan att skriva över varandra.
  • Konflikt på samma key ger 412/409 och bevarar båda användarnas osparade arbete.
  • Klienten kan inte byta schema eller accessresurs för att kringgå kontrollen.

Tester som skyddar beteendet

  • Behörighetsmatris för R, RW och ingen match på alla tre sektioner.
  • Integrationstest för GET, PUT, DELETE, full Errand, historik och handover.
  • Test av AccessMapper-fel: skyddade delar ska neka åtkomst.
  • Test av cacheinvalidering när en användares behörighet dras in.
  • Samtidighetstest för olika keys och samma key.

Det som inte behöver ändras

  • Errand behöver inga IAF-specifika fält.
  • JsonSchema fortsätter beskriva och validera data samt lagra UI Schema för presentation.
  • Labels kan fortsätta klassificera ärendet och styra åtkomst till hela ärendet.
  • Andra namespaces kan ligga kvar på nuvarande presentation bakom feature flag.

Risk och återställning

  • Inför målbilden per namespace/layout bakom feature flag.
  • Behåll JSON Parameter-datat oförändrat; ingen stor datamigrering krävs.
  • Vid rollback stängs den nya layouten, medan parametrarna ligger kvar.
  • Kort eller explicit invaliderad accesscache krävs för snabb återkallelse.
